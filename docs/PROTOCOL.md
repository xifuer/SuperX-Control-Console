# 协议笔记

本文记录本项目在 **壹号本 ONEXPLAYER SUPER X**（AMD Ryzen AI MAX+ 395）上实测得到的两个硬件接口。这些内容来自抓包与 EC 快照对比，不是厂商文档。

## 1. 机身材质灯（HID）

### 设备

| 项 | 值 |
| --- | --- |
| VID / PID | `1A2C` / `B001`（MI_00） |
| 用途页 / 用途 | `0xFF01` / `0x0001` |
| 输出报告长度 | 65 字节（含报告 ID） |
| 端点 | 中断 OUT `0x03` |

### 报文格式

Windows 下第一个字节是 **报告 ID**，必须为 `0x00`。载荷从第二个字节开始：

```
偏移  0     1     2     3 ...
     [00]  [07]  [FF]  <命令> <参数...>        共 65 字节，不足补 0
     │     │     │
     │     │     └─ 消息标识，固定 0xFF
     │     └─────── FID，固定 0x07
     └───────────── 报告 ID，固定 0x00
```

> 关键点：载荷里的 `07 FF` 经常被误当成报告 ID 和 FID 拆到前两个字节，导致整条报文左移一位，设备收下但完全不响应。用 USB 抓包对比厂商报文可以立刻确认。

### 命令

| 命令 | 名称 | 参数 |
| --- | --- | --- |
| `0xFC` | 读取状态 | 无 |
| `0xFD` | 设置状态 | `[启用, 速度, 亮度]` |
| `0xFE` | 单色 | 18 组 `[R,G,B]`（共 54 字节） |
| `0x00`–`0x13` | 内置特效 | `[特效编号]` |

### 参数范围

| 参数 | 范围 | 备注 |
| --- | --- | --- |
| 启用 | `1` / `0` | |
| 速度 | `0`–`9` | 仅对特效有效 |
| 亮度 | `0`–`3` | **上限是 3**，填 4 会被判为关闭 |
| 颜色 | `0`–`255` | 单色模式下用 RGB 缩放做亮度 |

### 回执

发送 `0xFC` 后从同一设备的中断 IN 端点读回 65 字节：

```
[00] [07] [0F] [xx] [xx] [特效] [启用] [速度] [亮度] [R] [G] [B] ...
                  │      │      │      │      │
                  │      │      │      │      └─ 当前颜色
                  │      │      │      └──────── 亮度 0–3
                  │      │      └─────────────── 速度 0–9
                  │      └────────────────────── 启用（非 0 即为开）
                  └───────────────────────────── 当前特效编号
```

即：**发送前用 0x00 占位，读取时数据整体后移一位**。用回执可以实现自检，不必依赖肉眼观察灯效。

## 2. 供电类型（EC 寄存器）

### 访问方式

标准 ACPI EC 时序，通过 `inpoutx64` 驱动完成：

```
状态口 0x66，数据口 0x62
1. 等待 0x66 的 IBF(bit1) 清零
2. 0x66 <- 0x80（读命令）
3. 0x62 <- 寄存器地址
4. 等待 0x66 的 OBF(bit0) 置位
5. 读 0x62
```

读取时可能因其他进程占用 EC 而超时，需要**多次重试**（本项目重试 4 次）。

### 寄存器 `0xFE`

| 值 | 含义 |
| --- | --- |
| `0x01` | 电池供电 |
| `0x03` | Type-C 供电 |
| `0x05` | DC-IN 供电 |

> 该寄存器在三种电源下取值稳定，且与系统 `ACLineStatus` 相互独立（插着 Type-C 时 `ACLineStatus` 为 1，但寄存器为 `0x03`）。

### 排除项

- 寄存器 `0xFD`：DC 时为 `0x04`，但 Type-C 与电池都是 `0x01`，无法区分
- 稳定寄存器全量对比（各取 5 次采样取交集）：除 `0xFE` 外无差异，说明供电类型只集中在这一个字节

## 3. TURBO 键

按下时键盘钩子收到的是组合键：

```
Ctrl + Win + Alt（VK_LMENU = 0xA4，扫描码 0x38）
```

EC 侧没有任何寄存器变化，因此它走的是键盘通道，不是 EC 事件。绑定逻辑用「扫描码 + 修饰键完全匹配」，这样单独的 Alt 不会误触发。

## 4. CompatLayerCT 命名管道（OneXConsole 硬件层）

OneXConsole 的所有硬件操作都在 `CompatLayerCT.exe` 里，通过命名管道对外提供。

### 启动

```
CompatLayerCT.exe <端口> OneXConsole 2
```

第三个参数 `2` 表示只开管道、不开 HTTP。**必须以普通用户身份启动**：用它自己的管理员上下文启动会自我退出；从提权进程间接启动需要经过资源管理器（例如写一个 VBS 用 `WScript.Shell.Run(..., 0, False)` 拉起）。

### 协议

```
管道：\\.\pipe\CompatLayerCT         （单客户端）
请求：{"id":"<uuid>","path":"/xxx/yyy","parameters":{...}}\n
响应：{"id":"<uuid>","code":1,"msg":null,"result":"<字符串>"}\n
事件：{"id":"__SocketBizEvent","code":1,"result":"{eventName,eventParams}"}\n
```

### TURBO 订阅

```
/keyboard/quickButtonHookStart/1     启动快速按键钩子
/func/takeOverTurboButton/true       让 EC 接管
```

之后按键会产生：

```json
{"eventName":"TurboButtonStatus","eventParams":["1"]}   // 按下
{"eventName":"TurboButtonStatus","eventParams":["0"]}   // 松开
```

### 已实测可用的其它路由

| 路由 | 返回 |
| --- | --- |
| `/info` | 机型、BIOS、EC 版本、HID 设备列表 |
| `/battery/getPowerSupplyMode` | 需要厂商初始化序列，未初始化时返回 `1000` |
| `/func/getOXPSensorInfo` | 同上，未初始化时全 0 |

### 两个坑

1. **EC 争用**：我们的程序直接读 EC（`0x62/0x66`）会打断 CompatLayerCT 的按键轮询，导致 `TurboButtonStatus` 丢失。共存时应降低读取频率（本项目降到 5 秒一次）。
2. **管道单实例**：OneXConsole 运行时管道被它占用，第三方无法连接；反过来我们的程序占着时 OneXConsole 也连不上。二者只能有一个作为管道客户端。
